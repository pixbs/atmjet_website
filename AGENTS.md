# ATM JET website: guide for AI agents and humans

This file is the single source of truth for every coding agent (Claude Code, Codex, Cursor, Copilot and others) and is imported by `CLAUDE.md`. Read it fully before changing anything. The Next.js block above is managed by `next dev`; leave it in place.

## 1. Hard rules (enforced by git hooks and the `conventions` check; violations are rejected, not reviewed)

1. **No AI attribution, anywhere.** Commit messages, pull request titles and descriptions, comments, branch names and code must not carry AI attribution: no `Co-Authored-By` trailers naming an AI tool or vendor, no "generated with", "generated by", "made by" or robot-emoji footers, no links to an AI tool or to an agent session, no vendor no-reply e-mail address as author or committer. Commits are authored as the repository owner identity configured in the environment; author and committer strings are checked against the same banned patterns (there is no allowlist to configure). The patterns live in `scripts/ci/attribution-patterns.txt`. Defence in depth, all automatic: the commit-msg hook strips attribution trailers and commitlint rejects the rest; the `conventions` workflow removes tool footers from pull request descriptions and the `scrub comments` workflow from comments before the scan, then fails on anything left (some agent platforms append such footers on every write, even through the API: do not try to remove them by hand, the workflow does it). For Claude Code, `.claude/settings.json` disables attribution and a pre-tool hook blocks offending commands.
2. **Branch names:** `<type>/<issue>-<kebab-slug>` with `type` one of `feat fix chore docs refactor test ci build perf revert`, for example `feat/42-hero-video-block`. Never `claude/...`, `codex/...`, `copilot/...`, `cursor/...` or any other tool prefix. If your environment created a branch with another name, create the correctly named branch from it and open the pull request from that branch.
3. **Commits:** Conventional Commits (`type(scope): lowercase subject`, at most 100 characters), one verified step per commit (lint, typecheck and the relevant tests pass at every commit), a body that explains why, and a footer `Refs #<issue>` (`Closes #<issue>` in the final commit of a pull request).
4. **Pull requests:** one pull request = one shippable slice: a page with the blocks it needs, a block with its components, a collection with the page or import that reads it, or one process change. A slice may close several issues (`Closes #a, #b`); an issue too large for one slice is split into slices that each say `Part of #<issue>`. Aim for 200 to 800 hand-written lines (generated files excluded); above 1,000, split. Merge each slice before starting the next; stack at most two open pull requests, each targeting the one below it. Title in Conventional Commits form, body from the template. Pull requests are squash-merged: `master` holds one commit per pull request, named after it. Never push to `master`, never force-push a shared branch, never rewrite `legacy` or the `legacy/*` tags.
5. **Data safety:** the legacy production database is read-only for this project and is never modified. In the new database the `legacy` schema is immutable. Drizzle push runs only under `bun run dev` (`NODE_ENV=development`), against the disposable local database; seeding, tests, CI, previews and production apply the committed migrations, each deployment to the database it reads: a preview migrates the Neon branch the Vercel integration creates for it, never production (`docs/adr/0008-lean-conventions.md`, #18). Every data import is idempotent, resumable and reconciled (`docs/adr/0002-database-migration-strategy.md`).
6. **Visual parity:** the rewrite must look exactly like the legacy site. Every ported section or page ships a visual test against the legacy baseline; behaviour changes are limited to the bugs listed in `docs/legacy-inventory.md` section 13 as `fix-while-porting`.

## 2. Engineering rules

- **SSR-first** (`docs/adr/0007-rendering-strategy.md`): server components by default; data through the Payload Local API on the server; the initial content of every page is server-rendered; filters and pagination are URL (`searchParams`) driven; `'use client'` only for leaf interactivity (forms, carousels, dialog shells, scroll state); `generateMetadata` on the server; caching through Payload `afterChange` hooks with `revalidateTag` / `revalidatePath`.
- **Tailwind discipline** (`docs/adr/0006-styling-and-motion.md`): design tokens live in `@theme` in `src/app/(frontend)/globals.css`; no arbitrary values such as `bg-[#14323d]`, add a token instead; variants with `cva`, merging with `cn()`; repeated class bundles become components; `@apply` and element selectors only in the documented parity base layer; Tailwind is imported only by the frontend layout, never by the admin; classes are sorted by Prettier.
- **Animation** (`docs/adr/0006-styling-and-motion.md`): `motion` is the only animation library. Use `m.*` components inside `MotionProvider`, the shared vocabulary in `src/lib/motion.ts`, `whileInView` for reveals and `AnimatePresence` for enter and exit. No CSS animation libraries, no `react-intersection-observer`.
- **Tests for behaviour** (`docs/adr/0004-testing-and-ci-strategy.md`, amended by ADR-0008): unit tests for logic (`tests/unit`), integration tests for collections, hooks and access control (`tests/int`), e2e for flows (`tests/e2e`), visual for UI (`tests/visual`), axe for accessibility (`tests/a11y`). A test asserts a behaviour the issue lists, never a constant, a type or an admin `condition` called directly. Coverage thresholds in `vitest.config.mts` are fixed numbers, not a ratchet.
- **Smallest diff that passes** (`docs/adr/0008-lean-conventions.md`): deliver only what the issue lists, nothing for a future issue. Reuse an existing helper before adding one; prefer the framework default (a Payload plugin, a Next cache function) over a custom layer. No export without a caller in `src/`. A comment is one sentence saying why, with a link to the ADR or inventory section, never a paragraph; an admin `description` is one line. Before opening the pull request, delete what nothing calls.
- **i18n** (`docs/adr/0003-i18n-strategy.md`): locales `en`, `ru`, `uk`; content is localized in Payload; a locale is public only when enabled in the site settings; no hard-coded language ternaries in components.
- **Payload:** collections in `src/collections`, globals in `src/globals`, blocks in `src/blocks`, shared fields in `src/fields`, queue tasks in `src/jobs`. After changing the config run `bun run generate:types` and `bun run generate:importmap`; create one migration per finished slice with `bun run migrate:create <name>`, never one per commit, and commit the results. Migration snapshots, `src/payload-types.ts` and the import map are generated files (`.gitattributes`), never edited by hand. Access control is explicit on every collection and covered by `tests/int/access.int.spec.ts`. Payload documentation: https://payloadcms.com/docs.

## 4. Commands (Bun)

| Command                                                              | Purpose                                                          |
| -------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `bun install`                                                        | install dependencies; also installs the git hooks (lefthook)     |
| `bun run dev`                                                        | dev server at http://localhost:3000, admin at `/admin`           |
| `bun run lint`, `bun run typecheck`, `bun run format:check`          | static checks                                                    |
| `bun run knip`                                                       | files, exports and dependencies nothing uses (part of `ci`)      |
| `bun run db:reset`                                                   | drop, migrate, clear the uploads and seed; refuses production    |
| `bun run migrate`, `bun run migrate:create <name>`, `migrate:status` | Payload migrations                                               |
| `bun run test:int`                                                   | unit and integration tests with coverage thresholds              |
| `bun run test:e2e`, `bun run test:visual`, `bun run test:a11y`       | Playwright tiers against the dev server or `PLAYWRIGHT_BASE_URL` |
| `bun run test:visual:update`                                         | regenerate visual baselines (Linux only)                         |
| `bun run test:lighthouse`                                            | Lighthouse budgets                                               |
| `bun run ci`                                                         | migrate (production only) and build (the Vercel build command)   |

Local database: `docker compose up -d` (Postgres 17) or any Postgres 16+; copy `.env.example` to `.env`.

## 5. Workflow

1. Take one slice: the issue, or the few issues, that ship together; read their legacy references in `docs/legacy-inventory.md`.
2. `git switch -c <type>/<issue>-<slug>` from `master` (the number of the main issue), or from the lower branch when stacking one level.
3. Implement in small verified commits and add the tests the issues list; delete what nothing calls before opening the pull request.
4. Push, open the pull request with the template and `Closes #<issue>` for every issue the slice completes; for a stack, set the base to the lower branch (`gh pr create --base <branch>`).
5. Make the `conventions` and `ci` checks pass; request the `run-e2e` label for browser tests on the preview deployment. Squash-merge, bottom-up for a stack: when the lower pull request merges and its branch is deleted, GitHub retargets the next one to `master`.
